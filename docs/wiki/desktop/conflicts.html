Resolve a merge conflict

When a merge, rebase or cherry-pick stops because both sides changed the same lines.

A conflict happens when two branches changed the same lines of the same file and git can't tell which version to keep. It stops in the middle of a merge, rebase, cherry-pick or revert and asks you. Nothing is broken and nothing is lost; you decide, and then git carries on.

In the conflicted file, git marks the two versions like this:

<<<<<<< HEAD
the version on your current branch (ours)
=======
the version from the other branch (theirs)
>>>>>>> other-branch

Resolving means ending up with the text you want, with all three marker lines gone. The two names matter for the Keep mine (ours) and Take theirs buttons below. In a merge, "ours" is the branch you are on and "theirs" is the one you are merging in. In a rebase they are the other way round: "ours" is the branch you are rebasing onto, and "theirs" is your own commit being replayed.

In canopy desktop#

When an operation stops on conflicts, Changes shows a banner (A merge is in progress., or rebase, cherry-pick or revert) and a Conflicts section listing each file. The banner says how many conflicts are left.

  1. Click a conflicted file. The right side explains what happened and offers four buttons.
  2. To choose line by line: click Open in editor, keep what you want between the markers, delete the marker lines, save, and click Mark resolved.
  3. To choose one whole side: click Keep mine (ours) or Take theirs. That replaces the file with that version and marks it resolved in one step.
  4. When the Conflicts list is empty, click Continue merge in the banner (it says rebase, cherry-pick or revert when that is what is in progress). The button is greyed out until every conflict is resolved.
  5. To give up, click Abort and confirm. Everything goes back to how it was before the operation started.
Mark resolved doesn't check the file. canopy stages whatever is in the file when you click it. Make sure the <<<<<<<, ======= and >>>>>>> lines are gone first, or they end up in your commit.
Open in editor uses the editor set in Settings (General). Change it there if the wrong program opens.

What git runs#

Choosing a whole side is the first two lines. Marking a file resolved is just the second. Continue and Abort use the command that matches the operation in progress.

$ git checkout --ours -- <file>      # or --theirs
$ git add -- <file>
$ git -c core.editor=true merge --continue
$ git merge --abort
$ git -c core.editor=true rebase --continue
$ git rebase --abort

For a cherry-pick or a revert, canopy runs cherry-pick or revert with --continue or --abort instead. core.editor=true keeps git from stopping to ask for a commit message.

If something goes wrong#

  • Continue is greyed out. A file is still listed under Conflicts. Resolve it with one of the four buttons and the button turns on.
  • Markers ended up in the file. Mark resolved doesn't check for them. Open the file, remove the marker lines, and stage it again from Changes. If you have already continued, fix the file and make a new commit or amend (see Fix your last commit).
  • Keep mine kept the wrong side. During a rebase, "ours" and "theirs" swap (see the top of this page). Click the other button. The file is already marked resolved, so open it from the Staged list and edit it there, or abort and start again.
  • It went badly and you want to start over. Click Abort. Nothing is lost. After the merge is finished, you can still take it back with the undo arrow: see Undo a mistake.
  • You'd like fewer conflicts. Pull often and keep branches short. See Branches, merging and rebasing.
