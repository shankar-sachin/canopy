Tag a version and publish a release

Mark a commit as v1.2.0, push the tag, and publish a GitHub release with notes.

A tag is a permanent name for one commit, such as v1.2.0. It marks "this is the version we shipped". A release is a page on GitHub built on a tag, with a title, notes and downloads.

The steps are always the same: tag the commit, push the tag, then create the release on GitHub. canopy console does all three.

Lightweight or annotated. A lightweight tag is only a name. An annotated tag also stores a message, your name and the date. Either works for a release. If you want a note attached to the tag, write a message.

In canopy console#

Tag a commit#

  1. Press 3 for History, select the commit and press T. Type the tag name, for example v1.2.0, and press ↵. This makes a lightweight tag.
  2. To tag the commit you have checked out, with a message, press 4 for Branches and ] until you reach Tags, then press n. Type v1.2.0, or v1.2.0: what changed for an annotated tag. Spaces in the name become -.
  3. Press P on the Tags view to push the selected tag. It goes to origin, or to the first remote. If there is no remote you get the message "No remote to push to".

Delete a tag#

  1. On the Tags view, select the tag and press d.
  2. Choose Delete locally to remove it from this computer only, or Delete here and on origin (the menu names your remote) to remove it from the remote too. esc cancels.

On the Tags view, space or ↵ checks out the tag after a confirmation. This puts you on the tagged commit with no branch, which is fine for looking around but not for new work.

Create a release#

  1. Push the tag first (see above). If the tag does not exist on GitHub, GitHub creates it for you on the default branch, which may not be the commit you meant.
  2. Press 0 for Actions, then ] to switch to Releases.
  3. Press n. The suggested tag is the next one: the latest published release with its patch number plus one (v1.0.13 becomes v1.0.14), or v0.1.0 if there is no release yet. Edit it or accept it with ↵.
  4. In the form, the title starts as the tag name. Write notes in the body, or leave the body empty and GitHub generates notes from the merged pull requests. Press ⌃S to publish, or ↵ while the cursor is in the title line. tab moves between the title and the body, and esc cancels.
  5. Select a release and press o to open it in your browser.
Published straight away. canopy never makes a draft release. The release goes live as soon as you submit, and needs gh to be signed in. You can edit or delete it on GitHub afterwards.

What git runs#

Tags use plain git. Releases use the GitHub command line, gh.

$ git tag v1.2.0 <commit>
$ git tag -a v1.2.0 -m "what changed" <commit>
$ git push origin v1.2.0
$ git tag -d v1.2.0
$ git push origin --delete refs/tags/v1.2.0
$ gh release create v1.2.0 --title "v1.2.0" --generate-notes
$ gh release create v1.2.0 --title "v1.2.0" --notes "what changed"

The first tag line appears when you give no message, the second when you do. Delete here and on origin runs the git push --delete line first and then git tag -d. Releases use --generate-notes when the notes are empty and --notes otherwise.

If something goes wrong#

  • The tag already exists. Tag names are unique. Pick a new name, or delete the old tag first. Moving a tag that others may have downloaded is best avoided.
  • "No remote to push to". The repository has no remote. Connect it to GitHub first: see Sync with a remote.
  • You pushed the wrong tag. On the Tags view press d and choose Delete here and on origin, then push the right one.
  • The release points at the wrong commit. That happens when the tag was not pushed before you created the release. Delete the release on GitHub, push the tag, and create it again.
  • Creating a release fails. Check that gh is signed in (gh auth status) and that you can write to the repository.
  • You tagged the wrong commit locally. Delete the tag and tag again. If you have not pushed it, nothing else is affected. For other mistakes see Undo a mistake.
