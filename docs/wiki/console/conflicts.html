Resolve a merge conflict

When a merge, rebase or cherry-pick stops because both sides changed the same lines.

A conflict happens when two branches changed the same lines of the same file and git can't tell which version to keep. It stops in the middle of a merge, rebase or cherry-pick and asks you. Nothing is broken and nothing is lost; you decide, and then git carries on.

In the conflicted file, git marks the two versions like this:

<<<<<<< HEAD
the version on your current branch (ours)
=======
the version from the other branch (theirs)
>>>>>>> other-branch

Resolving means ending up with the text you want, with all three marker lines gone. The two names matter for the ours and theirs keys below: in a merge, "ours" is the branch you are on and "theirs" is the one you are merging in. In a rebase they are the other way round: "ours" is the branch you are rebasing onto, and "theirs" is your own commit being replayed.

In canopy console#

When an operation stops on conflicts, Changes shows that a merge (or rebase, cherry-pick, revert) is in progress and lists the conflicted files under their own heading. canopy console resolves them one conflict at a time.

  1. Open Changes (2). Select a conflicted file and press ↵ to open the conflict panel, which shows each conflict with both sides.
  2. Press j and k to move between conflicts. For the one you are on, press o to keep ours, t to take theirs, or b to keep both (ours, then theirs).
  3. Changed your mind? Press u to put the conflict markers back in the file. Press e to edit the file by hand in your editor.
  4. When the last conflict in a file is settled, canopy stages the file for you. Press esc to go back to the list and open the next file.
  5. When no conflicted files are left, press C to continue the merge (or rebase, cherry-pick or revert).
  6. To give up, press X and confirm. Everything goes back to how it was before it started.

On the file list you can also settle a whole file at once: o keeps ours for the entire file, t takes theirs, and space marks a file you edited yourself as resolved (canopy refuses if markers are still in it).

What git runs#

$ git checkout --ours -- <file>      # or --theirs
$ git add <file>
$ git checkout -m -- <file>          # put the markers back
$ git -c core.editor=true merge --continue
$ git merge --abort

Choosing ours or theirs for a whole file is the first two lines. Choosing a single conflict rewrites the file itself, then stages it once none are left. For a rebase, cherry-pick or revert, canopy console runs that command's --continue and --abort instead of merge.

If something goes wrong#

  • "Still has conflict markers". canopy console won't mark a file resolved while <<<<<<< or >>>>>>> lines are in it. Edit them out (e), or choose a side with o or t.
  • "Select a conflicted file first". The cursor is on a file that isn't under the conflicts heading. Move to a conflicted file and try again.
  • Nothing happens when you press C. A file may still be listed as conflicted. Settle it, and C continues.
  • Ours kept the wrong side. During a rebase, "ours" and "theirs" swap (see the top of this page). Press u to restore the markers and choose again.
  • It went badly and you want to start over. Press X to abort. Nothing is lost. After the merge is finished, you can still take it back: see Undo a mistake.
  • You'd like fewer conflicts. Pull often and keep branches short. See Branches, merging and rebasing.
