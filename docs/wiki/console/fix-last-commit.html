Fix your last commit

A typo in the message, a forgotten file, or a fix that belongs in an older commit.

Everyone makes a small mistake in a commit: a typo in the message, a file you forgot to add, or a change that belongs in a commit from a few steps back. Git lets you fix all three, and canopy console keeps each fix to a few keys.

Fixing a commit really replaces it with a new one (it gets a new id). That is harmless while the commit is only on your computer. If you have already pushed it, read If something goes wrong first.

In canopy console#

The message or a forgotten file (the last commit)#

  1. To add a forgotten file, open Changes (2), select the file and press space to stage it. To fix only the message, stage nothing.
  2. Press A on Changes. A commit box opens with the last message filled in. Edit it if you want.
  3. Press ↵ on the summary line (or ⌃S from anywhere in the box) to send it. The last commit is replaced with one that has your new message and everything you staged.

Unlike a normal commit, amend never stages everything for you. It uses only what you staged.

A change that belongs in an older commit#

  1. Make the fix and stage it on Changes (2, then space).
  2. Open History (3), select the commit the fix belongs to and press F. canopy adds a new commit called fixup! … that holds your fix.
  3. With that same older commit still selected, press i to start an interactive rebase. The fixup! commit is the last row of the list.
  4. Move it up with Shift+K until it sits directly under the commit it fixes, press f to mark it fixup, then ↵ to run. The fix is folded into the older commit and the extra commit disappears.
Squash and fixup fold upwards. A row marked fixup or squash merges into the row above it in the box, which is why the fixup! commit has to sit right under the commit it belongs to. The first row can't be either.

What git runs#

These are the commands canopy console runs for the two fixes:

$ git commit -m "the new message" --amend
$ git commit --fixup=<commit>
$ git -c sequence.editor=… -c core.editor=true rebase -i --autostash <parent of that commit>

--amend replaces the last commit instead of adding one. --autostash puts uncommitted work aside during the rebase and brings it back afterwards.

If something goes wrong#

  • You amended and it was the wrong thing. Press z: the branch moves back to the commit as it was before, with your changes staged. See Undo a mistake.
  • You already pushed the commit. An amended commit is a different commit, so the next push is refused. canopy console then offers Force push (with lease), which replaces the remote copy with yours. Only do that on a branch nobody else is using; otherwise leave the old commit alone and make a new commit with the fix.
  • "Stage the changes you want to fold into this commit first". F needs something staged. Stage the fix on Changes and try again.
  • "No commits to amend yet". The repository has no commit. Make a normal commit with c first.
  • "That range contains merge commits". The interactive rebase won't run over merge commits, because it would flatten them. Select a commit that comes after the last merge.
  • "Clear the filter (esc) before rebasing". You are searching History. Press esc first.
  • The rebase stops with a conflict. See Resolve a merge conflict: resolve it and continue, or abort to go back to how it was.
