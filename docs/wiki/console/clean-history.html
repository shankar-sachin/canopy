Tidy up commits before sharing

Squash, reorder, reword and drop commits with an interactive rebase.

While you work you make commits like "wip", "fix typo" and "oops, forgot this". Before you share a branch (push it or open a pull request), you can tidy them: squash several into one, drop ones you don't want, reorder them. Git calls this an interactive rebase. It replays your commits one at a time, and for each one you choose what happens.

Only tidy commits nobody else has. Tidying replaces your commits with new ones. That is safe while they are only on your computer or on a branch only you use. If others have pulled them, rewriting them causes trouble, so leave shared history alone.

The five choices for each commit are: pick (keep it as it is), squash (merge it into the commit before it and combine both messages), fixup (merge it into the commit before it and throw away its message), edit (stop there so you can change it) and drop (delete it).

In canopy console#

  1. Open History (3) and select the oldest commit you want to change. The list shows newest first. The rebase covers the selected commit and every commit above it, up to your latest.
  2. Press i. An Interactive rebase box lists those commits, oldest first, each marked pick.
  3. Choose what to do with each commit. Move with j and k, then press p (pick), s (squash), f (fixup), e (edit) or d (drop; the message is crossed out). Squash and fixup fold a commit into the one above it in the box, so they aren't allowed on the first row.
  4. To reorder, press Shift+J or Shift+K to move the selected commit down or up.
  5. Press ↵ to run it, or esc to cancel without changing anything.

Changing a commit's message. The box has no reword choice. Mark that commit edit and run it. The rebase stops there. Press A on Changes, fix the message, send it, then press C to continue.

If it stops#

An edit commit, or a conflict, pauses the rebase. Changes shows that a rebase is in progress. Press C to continue when you are ready, or X to abort and get everything back the way it was.

Squash everything into one commit#

If you only want one commit out of several, a reset is quicker than a rebase. On History, select the commit just before the ones you want to combine, press r and choose s (Soft). The commits leave the branch and all their changes are staged together. Then press c on Changes and write one clear message. See Undo a mistake for what the reset choices mean.

What git runs#

canopy writes your choices into the list git would normally open in an editor, then runs the rebase without opening one:

$ git -c sequence.editor="cp <your list>" -c core.editor=true rebase -i --autostash <parent of the oldest commit>
$ git -c core.editor=true rebase --continue
$ git rebase --abort

core.editor=true means a squash keeps both messages without stopping to ask. --autostash sets uncommitted work aside during the rebase and puts it back after.

If something goes wrong#

  • "That range contains merge commits". An interactive rebase would flatten them, so canopy refuses. Select a commit that comes after the last merge.
  • "Can't rebase the root commit from here". Select a commit that has a parent.
  • "Clear the filter (esc) before rebasing". You are searching History. Press esc first, so the list is your real history.
  • The rebase stops with a conflict. Two of your commits changed the same lines in a way git can't combine. See Resolve a merge conflict, then continue, or abort.
  • You didn't like the result. Press z: a whole rebase counts as one action, and Undo moves the branch back to before it started. See Undo a mistake.
  • You already pushed these commits. After tidying, the branch and its remote copy have diverged, so the push box offers Force push (with lease). Use it only if nobody else builds on this branch.
